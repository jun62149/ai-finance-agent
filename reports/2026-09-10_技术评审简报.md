## 1. 项目定位与边界

**一句话**：在已答辩的本科毕设《基于 XGBoost 的 A 股选股分析系统》之上做二次开发，
把遗留量化系统升级为「量化引擎 + 金融知识库（Hybrid RAG）+ 受控 Agent（LangGraph）+ Web UI + 离线评测」。

**做了**：Quant API 契约化 → 新闻/公告知识库 → BGE-M3 向量 → BM25 → RRF → Reranker →
工具层 → LangGraph Agent → 单页 UI → 评测集与四组对照实验 → Docker 化。

**没做（明确边界，评审时请勿假定其存在）**：

- 没有重训/微调任何模型；`strong_prob` 的分类 recall≈0.0005 是**继承自毕设的已知缺陷**，未尝试修复；
- 没有多轮会话、没有流式输出、没有 request_id 级可观测性；
- 没有行情增量抓取（数据止于 2026-06-24）；
- 没有知识图谱 / SQL Agent / MCP 等高级能力（设计文档定位为"第二版"）。

## 4. 关键接口契约

### 4.1 错误码（`app/errors.py` + `app/tools/errors.py`）

| code | 触发 | HTTP |
| --- | --- | --- |
| `InvalidStockCode` / `StockNotFound` | 代码格式非法 / 基础表无此股 | 400 / 404 |
| `NoData` | 该股/该日无因子数据（**绝不回退 latest**） | 404 |
| `ModelUnavailable` | 模型文件缺失 | 503 |
| `HistoricalPredictionUnavailable` | 语义上不支持的历史预测 | 501 |
| `LLMUnavailable` | LLM key 缺失 / 网络失败（含重试后） | 503 |
| `ToolArgumentError` / `ToolNotFound` / `ToolTimeout` / `ToolNotAllowed` | 工具边界 | — |
| `EvidenceMetadataMissing` | 证据缺可追溯字段 | 500 |

### 4.2 工具契约（`app/tools/registry.py`）

```python
call_tool(name, **kwargs) -> {"ok": True, "result": ...}
                           | {"ok": False, "tool": name, "error": {"code", "message"}}
```

- 工具**永不抛异常**（含 `FileNotFoundError` 等意外异常 → 结构化）；
- 量化工具直接调用 API 同款 service，错误码一致（有测试守住）；
- `search_financial_knowledge(query, stock_code, doc_type, days, top_k)` 返回
  `{query, filters, count, has_evidence, results[], retrieval{...}, embedding_version}`，
  每条 result 含 `chunk_id/document_id/stock_code/doc_type/title/source/publish_time/url/content`
  + `dense/bm25/rrf/rerank` 四路分数 + `citation`。

### 4.3 检索管线参数（`app/config.py`，全部 env 可覆盖）

```text
DENSE_TOP_K=20  BM25_TOP_K=20  FUSION_TOP_K=15  RERANK_TOP_K=5  RRF_K=60
EMBEDDING_MODEL=BAAI/bge-m3  EMBEDDING_DIM=1024  EMBEDDING_VERSION=bge-m3-v1
```

## 5. 关键设计决策（含被否方案与代价）

| # | 决策 | 理由 | 被否决的替代方案 | 代价 |
| --- | --- | --- | --- | --- |
| D1 | LLM 不做量化计算，量化能力只经工具暴露 | 模型预测必须可复现、可测试 | 让 LLM 自行算/口算因子 | 工具参数解析需确定性代码 |
| D2 | 量化工具与 HTTP API **共用 service** | 语义/错误码不可能漂移 | 工具层重新实现一遍 | 工具层无独立优化空间 |
| D3 | 公告源改 **cninfo 官方**，东财降级为可选 | 东财公告正文主机对本地 IP 有连接级风控（实测成片断连） | 死等东财解封 / 换第三方库 | 正文为 PDF，需 pypdf 解析 |
| D4 | 向量库从 **Qdrant 本地模式迁到服务端** | 单进程文件锁（实测：另一进程连只读都打不开）+ 官方不建议 >2 万点 | 继续本地模式 | 需 docker 依赖 |
| D5 | 检索按 **chunk**，评测标签按 **document** | chunk 是检索单位、文档是语义单位 | 给每个 chunk 打标签 | 指标解释需说明口径 |
| D6 | 评测排名**按 doc 去重**后计算 | 否则同一文档多 chunk 会把 NDCG 顶到 >1（曾发生） | 不去重 | 精度指标偏低但可比 |
| D7 | Agent 计划**确定性**，LLM 只能追加工具 | 可预测、可复现、可审计 | 完全由 LLM 规划 | 灵活性受限 |
| D8 | 时间过滤用 `publish_ts`(epoch) 数值字段 | Qdrant 只能对数值/日期做区间过滤 | 后置过滤全部结果 | 需回填与写入派生 |
| D9 | `.env` 自实现加载（无 python-dotenv） | 零依赖、密钥不入库 | 引入 dotenv 包 | 不支持多行/变量展开 |
| D10 | CPU 镜像用 `--extra-index-url` 且**不设 `\|\|` 回退** | 回退会静默装入 CUDA torch + nvidia 全家桶（实测发生） | 允许回退 | 索引不可达时构建直接失败 |

## 7. 评测方法与结果

**指标**：Recall@K、Precision@K、MRR、NDCG@K（二值增益）、端到端延迟。
**相关性口径**：检索返回 chunk，命中"标签文档"即视为相关；**排名先按 `document_id` 去重**再算全部指标。

### 7.1 带元数据过滤（22/36 题带 stock_code、35/36 带 doc_type）

| 配置 | R@5 | R@10 | P@5 | MRR | NDCG@5 | 中位延迟 |
| --- | --- | --- | --- | --- | --- | --- |
| BM25-only | 0.4240 | 0.5069 | 0.3944 | 0.6672 | 0.5799 | 4 ms |
| Dense-only | 0.3784 | 0.4339 | 0.3222 | 0.5736 | 0.4767 | 63 ms |
| Hybrid(RRF) | 0.4109 | 0.5147 | 0.4000 | 0.6755 | 0.5817 | 68 ms |
| Hybrid+Rerank | **0.4747** | **0.5414** | **0.4500** | **0.7130** | **0.6464** | 376 ms |

### 7.2 不带过滤（更难）

| 配置 | R@5 | R@10 | P@5 | MRR | NDCG@5 | 中位延迟 |
| --- | --- | --- | --- | --- | --- | --- |
| BM25-only | 0.3094 | 0.4378 | 0.3222 | 0.5758 | 0.4667 | 4 ms |
| Dense-only | 0.2654 | 0.3534 | 0.2389 | 0.4470 | 0.3450 | 26 ms |
| Hybrid(RRF) | 0.3336 | 0.4264 | 0.3444 | 0.5611 | 0.4689 | 30 ms |
| Hybrid+Rerank | **0.3833** | **0.4736** | **0.3944** | **0.6435** | **0.5620** | 356 ms |

**自述结论**：① reranker 是单项收益最大组件（+0.06 R@5，+310ms）；② BM25 单独强于 dense 单独；
③ 融合在**无过滤**时更有价值（0.3336>0.3094），有过滤时反而略低于 BM25（0.4109<0.4240）；
④ 日期类查询不过滤时 dense R@5 掉到 0.0059；⑤ 语义类 dense(0.233)>BM25(0.206)。

**已自认的方法学局限**：标签由标题关键词生成 → 对词面匹配（BM25）天然略有利；
每类仅 5~11 题；无显著性检验；`code/name` 类查询与标签存在词面重合。

## 9. 我认为最值得评审的 10 个点（按风险排序）

> 每条给出：**现象 / 我的判断 / 可能的反例**。请优先验证与反驳。

1. **RRF 等权融合在过滤场景下劣于单路 BM25**（7.1：0.4109 < 0.4240）。
   *我的判断*：过滤已把候选压小、两路高度重合，`1/(k+rank)` 等权会稀释强信号，应改成加权或按意图调参。
   *可能的反例*：也可能是指标口径（doc 去重、K=5/10）造成的假象，需要做参数扫描（k∈{10,60,100}、权重扫描）才能定论。

2. **评测标签的生成方式对 BM25 有利**（标签来自标题关键词）。
   *我的判断*：`code/name/date` 三类结论"BM25 更强"可能被高估，语义类才反映真实差距。
   *可能的反例*：即便剔除词面重合题，BM25 仍可能占优（中文金融文本里精确 token 权重确实高）。

3. **BM25 的元数据过滤是后置过滤**（`bm25s` 无过滤能力，见 `bm25.py`）。
   *我的判断*：当过滤条件很窄时，`max(top_k*10, 200)` 的候选窗口可能不足，导致"明明有文档却召回 0"。
   *可能的反例*：当前语料单股文档数有限（~100~300），窗口通常够用；需要构造窄过滤用例实测。

4. **`clean_text` 静默截断 200,000 字符**（11 篇年报受影响，占公告 1.1%）。
   *我的判断*：应在截断时留痕（字段标记或分片多文档），否则"检索不到"与"文档没有"无法区分。
   *可能的反例*：对 RAG 召回而言尾部页码（财务报表附注）价值低，影响或许可忽略——但**不可观测**本身就是缺陷。

5. **BM25 索引与向量库的一致性依赖人工重建**。
   *我的判断*：`build_bm25.py` 按 `embedding_version == 当前版本` 建索引；若换了 embedding 版本而忘记重建 BM25，
   两路召回会落在不同 chunk 集合上，融合结果无法解释（且不会报错）。
   *可能的反例*：目前版本固定为 `bge-m3-v1`，短期不会触发；但这是**静默失败**型风险。

6. **`_plan_arguments` 对多股票场景只取 `codes[0]`（已知未修）**。
   *我的判断*：`stock_comparison` 意图名不副实——"比较 A 和 B"实际只查了 A，属于功能性缺陷。
   *可能的反例*：LLM 可在 `tool_execution_loop` 里追加第二次调用补上，但**不能依赖**（默认不加）。
   建议修法：planner 对 stock 类工具按 `stock_codes` 展开成多个调用。

7. **文件锁/并发模型**：迁移到 Qdrant 服务端解决了向量库并发，但 SQLite 仍是单文件写。
   *我的判断*：`ingest_*` 与 API 同时运行时，写入（`embedding_version` 更新）可能与读冲突（默认 journal 模式）。
   *可能的反例*：写操作短且低频；建议启用 WAL 而非复杂化架构。

8. **Agent 的确定性计划 vs LLM 追加调用的边界**。
   *我的判断*：`MAX_ITERATIONS=6` 的语义是"LLM 最多追加 5 轮"，但代码中 `iterations` 只在 LLM 分支自增，
   计划工具耗尽后即退出——边界描述与实际行为是否一致值得审阅。
   *可能的反例*：这是刻意的（计划工具不属于"轮次"），但注释与实现需对齐。

9. **`evidence_validator` 的判定规则偏保守**：`intent ∈ {analysis, comparison, ranking}` 时
   缺少量化结果即 `evidence_ok=False`，即便问题其实只需文本证据。
   *我的判断*：宁可保守也不该放行无证据的量化结论；但可能造成"证据充足却标记不足"的误报。
   *可能的反例*：可从 36 题的人工判读中统计误报率。

10. **评测集与语料的耦合**：标签冻结在 JSON，但语料若重新采集（时间推移、公告更新），
    标签会指向不存在的 document_id。
    *我的判断*：需要"标签失效检测"（评测前校验标签可达性），否则指标会静默虚低。
    *可能的反例*：当前未重新采集，问题未显现。

## 10. 已发现并修复的缺陷清单（供判断代码成熟度）

| # | 缺陷 | 影响 | 修法 |
| --- | --- | --- | --- |
| 1 | cninfo 分页 `pageSize>30` 时服务端忽略 `pageNum` | 每只股票只拿到最新 ~30 篇（应为 ~94），语料静默缺失 2/3 | 钳制 30 + 按 announcementId 去重 + `hasMore` 驱动 + 回归测试 |
| 2 | NDCG > 1（1.19） | 指标不可信 | 排名按 document 去重后计算 + 回归测试 |
| 3 | **`publish_ts` 未在写入时派生** | 回填之后新写入的点对 `days`/日期过滤**完全隐身**（静默） | 在唯一写入收口 `upsert_chunks` 中派生 + 回归测试 |
| 4 | `call_tool` 只捕获 `QuantError` | 缺索引/缺模型等异常会击穿 Agent 循环 | 兜底捕获为结构化错误 |
| 5 | 本地 Qdrant `delete+create` 复活旧点 | `--recreate` 不生效 | 追加显式 `purge()`（filter 删除） |

## 13. 本项目自认"不成立 / 不要采信"的说法

1. ~~"本地 Qdrant 模式比服务端慢"~~ —— **已被实测推翻**：热态下两者 dense 中位延迟 31ms vs 36ms，
   迁移的真实理由是**单进程文件锁**与官方 2 万点建议，不是延迟。
2. ~~"hybrid 一定优于 BM25"~~ —— 有元数据过滤时 hybrid(RRF 等权) **略低于** BM25-only。
3. ~~"dense 检索更适合金融文本"~~ —— 本语料/题集上 BM25-only 全面优于 dense-only（语义类除外）。
4. ~~"strong_prob 是上涨概率"~~ —— 分类 recall≈0.0005，仅为弱信号辅助字段。
5. ~~"量化数据是最新的"~~ —— 止于 2026-06-24，而新闻/公告到 2026-09，**两者不同时点**。
