## 0. 新增测量数据（本方案的设计依据）

### 0.1 方案 A 的性能代价（真实语料 109,554 chunks，5 个查询取中位）

| BM25 候选窗口 | `retrieve()` 耗时 | 含"过滤到 20 条"总耗时 |
| --- | --- | --- |
| 200（当前） | 0.4 ms | **0.6 ms** |
| 1,000 | 0.5 ms | 1.4 ms |
| **5,000** | 0.7 ms | **1.8 ms** |
| 20,000 | 3.1 ms | 4.2 ms |
| 109,554（全量，无窗口） | 10.0 ms | **11.9 ms** |

> 对照：dense 单次约 26~63 ms。**即使完全取消窗口，BM25 也只有 ~12ms，仍比 dense 便宜一个数量级。**

### 0.2 方案 B 的成本（分片索引）

```text
语料覆盖股票数：32 只（不是 1,044 —— RAG 语料只有 32 只）
每片 chunk 数：中位 2,756 / 最大 12,537 / 最小 763
单股票(000725, 5,059 chunks) 建索引：6.12s ｜ 查询：0.7ms
32 片一次性构建 ≈ 3.3 分钟；存储量级与现有单索引相当（每片有独立词表开销）
```

### 0.3 方案 C 的关键障碍（中文分词）

Qdrant 的原生 BM25 稀疏向量（`fastembed` 的 `Qdrant/bm25`）使用**英文式分词**（按非字母数字切分、不分词），
对中文语料等于**按整段/整句成词**，效果极差 —— 必须自研 sparse encoder（jieba 分词 + 自算 BM25 权重）。
因此 C 的迁移成本**不在 Qdrant，而在中文稀疏编码器**（详见 §1.3）。

## 1. Issue 1：BM25 后置过滤漏召回（P1）

**问题回顾**：BM25 在「全局词面 top-200」内过滤，窄过滤条件（单股票+类型）下命中可为 0；
实测 `'公告' + 000333 + announcement` → 窗口版 **2** vs 全量 **356**（16/16 组合均有损失）。
Dense 则是「Qdrant 内过滤后检索」。**候选空间不对称。**

### 1.1 方案 A：扩大/取消窗口

| 字段 | 内容 |
| --- | --- |
| **最小修复** | `window = min(len(chunk_ids), max(top_k * 10, 200))` → **`window = len(chunk_ids)`**（过滤时全量打分后再过滤），保留一个 `BM25_WINDOW` 配置作为未来的降级开关。 |
| **推荐方案** | 同"最小修复"，理由是**它同时消除了语义缺陷与一个隐形参数**：过滤后再无"候选上限"这一概念，BM25 的候选空间与 dense 在语义上对称（都是"过滤后全量"）。代价见 §0.1：**+11ms**（0.6 → 11.9ms）。<br>若担心未来语料增长（>1M chunks），把 `BM25_WINDOW` 默认设为 `0 = 不限制`，超过阈值时由配置显式收紧并在日志中告警。 |
| **涉及文件** | `app/rag/bm25.py`（`search` 的 window 计算 + docstring）；`app/config.py`（新增 `BM25_WINDOW`，默认 0=全量） |
| **修改范围** | 约 5~10 行 + 配置项 1 行；不改接口签名 |
| **是否需要重建数据/索引** | **不需要**（索引与元数据不变，纯查询侧改动） |
| **是否需要重跑评测** | **需要**（BM25 与 Hybrid 的召回都会上升 → 四组对照数字全部变化） |
| **可能引入的新风险** | ① 单查询延迟从 0.6ms → 11.9ms（相对增幅大、绝对值小，可接受）；② 语料继续增长时线性变慢（1M chunks 约 100ms 量级）→ 用 `BM25_WINDOW` 兜底；③ 召回变多后 RRF 的候选池变化，可能改变融合排序（需与 Issue 3 的参数一起重测） |

### 1.2 方案 B：分片索引（按 stock_code / doc_type）

| 字段 | 内容 |
| --- | --- |
| **是否值得** | **当前不值得**：语料只有 32 只股票、109k chunks，方案 A 已用 +11ms 解决问题。分片带来的是**多一层路由与一致性维护**（32 个索引文件、各自 manifest、查询前要确定分片、跨股票查询无法路由），复杂度换来的收益（0.7ms 查询）在当前规模下没有意义。 |
| **何时值得** | 语料扩到**数千只股票 / 百万级 chunk**、且绝大多数查询都带 stock_code 过滤时。此时按 stock_code 分片能把单次检索从 100ms 级降到 1ms 级。 |
| **涉及文件（若做）** | `app/rag/bm25.py`（build/load/search 支持 shard key）、`scripts/build_bm25.py`（多分片构建）、retrieval 层的分片路由 |
| **重建/评测** | 需重建索引（≈3.3 分钟，32 片）＋重跑评测 |
| **新风险** | 分片路由错误 → **静默 0 召回**（比现在的窗口问题更隐蔽）；跨股票查询需回退到全量索引（两份索引并存，一致性更难保证） |

### 1.3 方案 C：Qdrant 稀疏向量（原生 BM25）

| 字段 | 内容 |
| --- | --- |
| **是否符合当前规模** | 技术上符合，但**收益与成本不匹配**：它解决的是"过滤对称 + 免维护独立索引"，而我们已能用 10ms 在客户端做到同等效果。 |
| **迁移成本（真实清单）** | ① **中文分词/权重自研**：`fastembed` 的 `Qdrant/bm25` 不切中文，必须自写 sparse encoder（jieba 分词 → 词频 → BM25 权重 → `SparseVector(indices, values)`），并维护 vocab↔index 映射；② **collection 必须重建**（Qdrant 不支持给已有 collection 追加命名向量）→ 需要重新 upsert 109,554 点；dense 向量可从现存**本地模式副本**（`data/qdrant`）逐点复制，**无需重新过 GPU**；③ 新增依赖 `fastembed`（或完全自研则无新依赖）；④ 写出/查询路径、测试、文档全部要改。 |
| **涉及文件** | `app/rag/vector_store.py`（命名向量 + sparse query + filter）、`app/rag/bm25.py`（改为 sparse encoder 或新增模块）、`scripts/build_bm25.py`（改为写稀疏向量）、`scripts/migrate_qdrant.py`（重建 collection 的迁移路径）、`app/rag/hybrid.py`（融合输入变化） |
| **重建/评测** | 重建索引（含 collection）＋重跑评测；预计 1~2 个工作日 |
| **新风险** | ① 自研 sparse encoder 的正确性（分词/权重口径）会直接决定检索质量，缺少现成基线可比对；② 一次性把"能解释清楚的 bm25s 统计"换成自研实现，面试可解释性反而下降；③ 本地模式副本与线上 collection 的版本漂移 |

### 1.4 Issue 1 结论

```text
✅ 采用方案 A（窗口取消/全量）。理由：+11ms 的实测代价、零索引重建、语义对称、参数更少。
❌ 方案 B：当前规模不值得（复杂度换 0.7ms）。
❌ 方案 C：中文分词自研 + collection 重建，成本与收益不匹配；作为"语料上百万级"时的演进方向记录在案。
```

## 2. Issue 2：评测公平性（P1）

**问题回顾**：官方脚本里 BM25/Dense 取 10 个 chunk，Hybrid 是 20+20→融合 15→截 10；
因同文档多 chunk，10 个 chunk 常只覆盖 3~8 篇文档，而指标按 **document 去重**计算 → 预算不等直接扭曲 recall。

### 2.1 参数语义：拆成三个

| 参数 | 含义 | 默认 |
| --- | --- | --- |
| `--candidate-k` | **每路召回深度**（dense、bm25 各取多少 chunk） | 20 |
| `--fusion-k` | 融合后保留多少 chunk（= 进入 rerank 的候选数） | = `candidate-k` |
| `--final-k` | **最终返回 / 参与指标的 chunk 数（四配置必须一致）** | 20 |
| `--k-values` | 指标 K（5,10），约束 `max(k_values) ≤ final-k` | 5,10 |

**理由**：把"每路取多深"（影响召回质量）与"最终交多少给下游"（影响成本与指标口径）解耦。
当前二者混在一个 `--top-k` 里，正是这次口径缺陷的根源。

### 2.2 四组实验重新定义：**统一 chunk 预算**（而非 document 预算）

```text
BM25-only      : bm25(candidate-k)                         → 截到 final-k
Dense-only     : dense(candidate-k)                        → 截到 final-k
Hybrid         : dense(candidate-k) + bm25(candidate-k) → RRF → final-k
Hybrid+Rerank  : dense(candidate-k) + bm25(candidate-k) → RRF(candidate-k) → rerank → final-k
```

**为什么统一 chunk 而不是 document 预算**：

1. 系统对外返回给 LLM 的**就是 chunk**，成本口径天然是 chunk（token 预算也按 chunk 算）；
2. chunk 级检索器**无法定义 document 预算**（要凑满 N 篇文档就必须做 doc 级聚合检索，那是另一种系统）；
3. document 去重只应作为**指标口径**（避免一文档多 chunk 刷分），不应反过来约束检索预算；
4. 统一 chunk 预算后，仍需**同时报告"平均不同文档数"**，让读者看到去重效应（实测：20 chunk 平均覆盖 14~15 篇文档，而 10 chunk 只覆盖 3~8 篇）。

### 2.3 README 实验表如何修改

1. 标题改为「**等 chunk 预算（candidate-k=final-k=20，指标 K=5/10）**」；
2. 新增两列：`avg unique docs`（每配置平均覆盖文档数）与 `chunk budget`（固定 20，写在表头说明）；
3. 保留两套表：**带过滤**（Agent 实际用法）与**不带过滤**（纯检索难度），与现状一致；
4. 增加一行脚注说明**旧表的缺陷**（预算不等导致 BM25/Dense 被低估）与新旧数字对照，**不隐藏**这次修正；
5. 若 Issue 3 的参数扫描产生新默认值，表中同步更新并在脚注写明选参依据。

| 字段 | 内容 |
| --- | --- |
| **涉及文件** | `scripts/evaluate_retrieval.py`（参数拆分 + 预算统一 + 新增 `unique docs` 统计）、`app/rag/eval_metrics.py`（可选：返回 `unique_docs` 诊断字段）、`README.md`（表格与脚注） |
| **修改范围** | 评测脚本 ~60 行、metrics ~10 行、README 表格重写 |
| **重建数据/索引** | 不需要 |
| **重跑评测** | **必须**（这是口径修正本身）；同时需要一份"新旧口径对照"留档 |
| **新风险** | ① 修正后**结论可能改变**（等预算下 BM25-only 0.4351 > RRF k=60 0.4248）→ README 的结论叙述必须同步改，否则变成"用旧口径讲故事"；② `--k-values` 与 `--final-k` 不一致时需显式报错，避免再次出现口径混淆 |

## 4. Issue 4：UTC / 时区（P2）

| 字段 | 内容 |
| --- | --- |
| **语义选择（金融场景理由）** | "最近 7 天"在金融语境下是**市场日历日**（A 股按北京时间划分交易日与披露日），不是 UTC 日。因此**日期语义固定为 UTC+8（CST）**；`publish_ts` 存的是"该文档所属市场时刻"的 epoch。<br>选 **固定 `timezone(timedelta(hours=8))`** 而不是 `ZoneInfo("Asia/Shanghai")`：中国无夏令时，固定偏移等价且**不引入 `tzdata` 依赖**（Windows 无系统 tz 数据库，`zoneinfo` 会因缺 tzdata 在换机器时炸——这本身就是一个"开发机能跑、换机器会炸"的点）。 |
| **最小修复** | 只把 `_date_to_epoch` / `publish_ts_from` 的转换显式加 `CST` 时区（`datetime.strptime(...).replace(tzinfo=CST).timestamp()`），并重跑一次回填。 |
| **推荐方案** | 同最小修复，另加三处一致性约束：<br>① `retrieval.hybrid_search` 的 `days` 计算改用 **CST 的 today**（`datetime.now(CST).date()`）而非进程本地 today（跨零点时区不同会差一天）；<br>② 在 `docker-compose.yml` 中显式 `TZ=Asia/Shanghai` 作为**防御**（代码已不依赖进程时区，此设置仅为日志可读性）；<br>③ 单测固定断言：同一日期字符串在任意进程时区下 epoch 相同（用 `TZ=UTC` 与 `TZ=Asia/Shanghai` 两个子进程各跑一次断言）。 |
| **涉及文件** | `app/rag/vector_store.py`（时区常量与两个转换函数）、`app/rag/retrieval.py`（`days` → CST today）、`docker/docker-compose.yml`（TZ 防御）、`tests/unit/test_indexing.py`（时区断言） |
| **修改范围** | ~15 行代码 + 1 个测试文件 |
| **是否需要重建数据/索引** | **必须重跑 `scripts/backfill_publish_ts.py`**（存储值口径变化；109,554 点，上次实测 282s）。BM25 索引不受影响（它用字符串日期比较，不依赖 epoch）。 |
| **是否需要重跑评测** | 不需要（评测集不含 `days`/日期过滤）。但**需要 Docker 复测**日期窗口行为。 |
| **新风险** | ① 回填期间若 API 在跑，会出现"新旧口径并存"的短暂窗口 → 建议停机回填或用 Maintenance 模式；② 若未来引入**海外市场**数据，"固定 +8" 就是错的，届时应升级为 per-market 时区字段（记入技术债，不在本期做） |

## 7. 明确不做的事（避免过度设计）

1. **不做** 分片索引（方案 B）：当前 32 只股票规模下收益 0.7ms，复杂度不划算。

4. **不做** 每次检索时的一致性校验：只在加载时校验一次。
5. **不做** 多市场时区抽象：当前只有 A 股，固定 UTC+8；若未来接海外数据再升级（已记入技术债）。
