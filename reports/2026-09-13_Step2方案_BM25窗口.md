## 0. 问题回顾（一句话）

BM25 现在是「**先在全库取词面 top-200，再按 metadata 过滤**」；Dense 是「**在 Qdrant 内过滤后检索**」。
候选空间不对称 → 窄过滤条件下 BM25 静默漏召回（实测 `'公告'+000333+announcement`：**窗口版 2 命中** vs 全量 **356**）。

---

## 1. 方案对比

| 维度 | **A. 全量 BM25**（`BM25_WINDOW=0`） | **B. 扩大窗口**（如 5000） | **C. metadata-aware BM25**（分片/稀疏） |
| --- | --- | --- | --- |
| 做法 | 取消候选截断，全库打分后再过滤 | 保留截断，只把上限调大 | 按 stock_code/doc_type 分片索引，或改用 Qdrant sparse（过滤下沉） |
| 代码复杂度 | **极低**：window 计算改为读配置（约 5~10 行） | **极低**：改一个默认常量 | **中~高**：分片需路由 + 多索引一致性；sparse 需中文分词自研 + collection 重建 |
| 性能影响（109k，实测） | 0.3ms → **~8~20ms**（见 §3） | 0.6ms → ~1.8ms | 分片 0.7ms；sparse 需重算 109k 稀疏向量 |
| 109k chunks 是否需要该优化 | **不需要**（全量已在 20ms 内，且 dense 本身 26~63ms） | 不需要 | 不需要（收益被 dense 淹没） |
| 百万 chunks 是否可接受 | 线性外推 **~100~190ms**：偏高但可接受（届时用 `BM25_WINDOW>0` 或分片降级） | 可控（窗口固定） | 推荐（这才是它的适用规模） |
| 正确性保证 | ✅ **无截断**，语义上与 dense 对称（过滤后全量） | ❌ **治标不治本**：仍是"全局词面 top-N"，N 与过滤选择性无关，**无法证明不漏**，只是把门槛推高 | ✅ 但要重新验证分词/权重口径 |
| 可解释性 | ✅ 少一个隐形参数，一句话讲清："BM25 全库打分，过滤在打分之后" | ⚠️ 面试会被问"为什么是 5000"，且答不出正确性 | ⚠️ 复杂度上升，讲清需要更长时间 |
| 风险 | 语料增长后延迟线性上升（有配置兜底） | **静默退化风险仍在**（正是这次要消灭的东西） | 分片路由错误 → 更隐蔽的 0 召回 |

### 1.1 推荐：**方案 A**

理由（按权重排序）：

1. **正确性**：只有 A 真正消除了"候选截断"这一失效模式；B 只是把阈值推高，**无法证明不漏**，与本次修复目标（消灭静默漏召回）不一致；
2. **成本**：A 的实测代价是 **+6~19ms**（最坏 p95 27.5ms），远低于 100ms 红线，也仍低于 dense 单路成本；
3. **可解释性**：A 让 BM25 与 Dense 的语义对称（都是"过滤后全量检索"），少一个隐形参数；
4. **不引入新依赖/新索引**：零数据重建、零迁移。

### 1.2 方案 B 的去处：**作为 A 的降级开关，而不是默认值**

评审上一条要求"保留 `BM25_WINDOW` 作为未来扩展参数"——这正好给了 B 一个正当位置：

```text
BM25_WINDOW=0    （默认）不限制窗口 = 方案 A
BM25_WINDOW>0    限制候选窗口，并在日志中 WARNING 声明"已触发截断"
```

即：**默认正确（A），需要时可用（B），且一旦启用必须留痕**。这样"语料增长后静默退化"就变成了"显式配置 + 显式告警"。

### 1.3 方案 C：明确不做（记录演进路径）

- **C1 分片索引**：当前语料只有 **32 只股票**、109k chunks；分片收益是 0.7ms vs 18ms，而 dense 本身要 26~63ms —— 收益被淹没，复杂度（32 个索引 + 路由 + 一致性）不划算。
- **C2 过滤后子集打分（重算 IDF）**：会改变 BM25 的统计口径（IDF 依赖全库），检索结果与离线评测不再可比 —— **不做**。
- **C3 Qdrant sparse**：`fastembed` 的 `Qdrant/bm25` **不切中文**，必须自研 jieba+BM25 权重编码器；且 Qdrant 不支持给已有 collection 追加命名向量，**必须重建 collection**（109,554 点重新 upsert）。
- **结论**：C 的适用规模是"数千只股票 / 百万级 chunk"，记入 `docs/TODO.md` 的演进方向，不在本期做。

## 2. 方案 A 的实施细节（待评审通过后执行）

### 2.1 代码改动点

| 文件 | 改动 | 预估行数 |
| --- | --- | --- |
| `app/config.py` | 新增 `BM25_WINDOW`（默认 `0` = 不限制） | +2 |
| `app/rag/bm25.py` | `search()`：`window = len(chunk_ids) if BM25_WINDOW <= 0 else min(len, BM25_WINDOW)`；记录 `scored / after_filter / truncated`；更新 docstring（明确"先打分后过滤"） | ~15 |
| `app/log.py` | 新增 `get_logger(name)`（项目当前**没有任何 logging 配置**，只有 legacy 的 `write_log()` 文件日志 → 需 6 行 basicConfig 兜底，让 INFO 可见） | +8 |
| `app/rag/retrieval.py` | 把 BM25 诊断字段并入 `hybrid_search` 返回值（`bm25_scanned / bm25_after_filter / bm25_window`） | ~6 |
| `app/tools/rag_tools.py` | 将上述字段透传到 `retrieval{}` → 出现在 Agent trace 与评测 JSON 中 | ~4 |
| `tests/unit/test_hybrid_retrieval.py` | 新增窗口语义测试（0=全量、>0=截断并告警、截断时仍返回过滤后结果） | ~40 |

### 2.2 日志格式（评审要求）

```text
BM25 search: window=ALL candidates_before_filter=109554 candidates_after_filter=356 returned=20 elapsed_ms=10.0
BM25 search: window=5000 (TRUNCATED) candidates_before_filter=5000 candidates_after_filter=12 returned=12 elapsed_ms=1.8
```

- **`window=ALL` 时 INFO**；**`window>0` 且真的发生截断时额外 WARNING**（"corpus has grown; candidate truncation is active"）；
- 同时把同名字段放进 `search_financial_knowledge` 的返回 `retrieval{}` —— 这样 **UI 的执行轨迹、评测 JSON、Agent 报告都能解释"这次 BM25 看了多少候选"**，而不只是服务端日志。

### 2.3 不改的东西

- 不改 `tokenize()`、不改 BM25 打分公式（bm25s 默认 k1/b）、不改索引格式 → **无需重建索引**；
- 不改过滤语义（stock/doc_type/date 仍是检索后过滤，但已无截断）。

## 3. 延迟对比（实测，回答"是否出现 100ms+ 增长"）

测量条件：真实语料 **109,554 chunks**，每场景 5 次取中位；`window=None` 即修复后的全量行为。

| 场景 | 窗口 200（现状） | 全量（修复后） | 延迟增量 | 过滤后命中 |
| --- | --- | --- | --- | --- |
| 普通 query（无过滤） | 0.3 ms（p95 7.7） | **19.6 ms**（p95 27.5） | +19.3 ms | 20 → 20 |
| 带 `stock_code`+`doc_type` | 8.6 ms | **18.1 ms** | +9.5 ms | **2 → 20** ⬅ 本次修复的核心收益 |
| 带 `date_from` | 2.1 ms | **8.0 ms** | +5.9 ms | 20 → 20 |
| 带 `stock`+`doc_type`+`date` | 0.3 ms | **10.0 ms** | +9.6 ms | 17 → 20 |

**结论**：

1. **没有 100ms+ 级别增长**。最坏中位 **19.6ms**、p95 **27.5ms**；
2. 增量集中在 **+6~19ms**，仍然**低于 dense 单路（26~63ms）**，因此 hybrid 的总延迟不会出现量级变化；
3. 收益是决定性的：`stock_code + doc_type` 场景从 **2 命中 → 20 命中**。

> 补充：普通 query 在窗口 200 时延迟仅 0.3ms（只排序 200 条），全量后 19.6ms —— 这是本次唯一"变慢明显"的场景，
> 但绝对值仍远低于 dense，且换来的是**任何过滤组合下都不再静默漏召回**。

## 4. 完成后的验证顺序（按评审要求，逐级放行）

```text
① 单元测试       新增窗口语义测试 + 全量测试套件（预计 166 → ~172 passed）
② BM25 单独 smoke  复现审计案例：'公告' + 000333 + announcement
                    期望：窗口 200 → 2 命中；修复后 → 与全量一致（356 可达，top-20 内 20 命中）
③ 延迟对比        重跑 §3 的四个场景，确认与方案预期一致（±20% 内）
④ 36 题评测       先 filtered，再 unfiltered；产出 docs/evaluation_after_fix.md
```

**④ 的关键验收判据（新增）**：

- **不带过滤的评测数字应当与 Step 1 的等预算结果完全一致**（无过滤时窗口本来就等于 `top_k`，
  全量后的前 20 名不变）—— 若不一致，说明改动引入了非预期行为，必须停下来定位；
- 带过滤的数字应整体上升（尤其 `code`/`doctype`/`date` 三类），`dense` 一列应保持不变（它不受影响）。

## 5. 风险与新问题

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| BM25 候选变多 → RRF 融合行为变化 | 融合结果会变，Step 3 的 RRF 选参必须在**新口径**下做 | 顺序本来就是 Step2 → Step3，符合评审设定 |
| 语料增长后延迟线性上升 | 百万 chunk 约 100~190ms | `BM25_WINDOW>0` 降级 + 截断告警；百万级时再评估分片（C1） |
| 诊断字段增加返回体体积 | 只增加 3 个整数字段，可忽略 | —— |
| 每次检索一行 INFO 日志 | 当前 QPS 极低（演示/评测），无影响 | 若未来高频，可降为 DEBUG + 仅截断时 WARNING |
| 全量扫描下 `candidates_after_filter` 可能很大（如 673） | 仅记录计数，不落内容 | 日志只输出整数 |
