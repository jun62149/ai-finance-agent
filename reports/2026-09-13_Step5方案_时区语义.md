## 2. 目标语义与实现方式

**语义**：金融场景下的"最近 N 天"是**市场日历日**（A 股按北京时间划分披露日与交易日），因此统一按 **UTC+8**。

**实现**：固定偏移 `timezone(timedelta(hours=8))`，**不用 `ZoneInfo("Asia/Shanghai")`**：

- 中国无夏令时 → 固定偏移与地区时区**等价**；
- `ZoneInfo` 在 Windows 上需要额外 `tzdata` 包，**换机器可能直接炸**（这正是"开发机能跑、换机器会炸"的典型），固定偏移零依赖。

**新增单一来源**（`app/timeutil.py`，约 20 行）：

```python
CST = timezone(timedelta(hours=8))
def market_today() -> date            # 市场日历"今天"
def to_market_epoch(value) -> int     # 日期/时间字符串 → 市场时刻 epoch
def market_stamp() -> str             # 审计时间戳（统一口径）
```

**改动点**（小改动，逐个替换）：

| 文件 | 改动 |
| --- | --- |
| `app/rag/vector_store.py` | `_date_to_epoch`/`publish_ts_from` 改用 `CST` |
| `app/rag/retrieval.py` | `days` 用 `market_today()` |
| `app/rag/sources.py` | `_cninfo_ts_to_date` 用 `fromtimestamp(ms/1000, tz=CST)` |
| `scripts/ingest_*.py`、`update_daily.py` | `date.today()` → `market_today()` |
| `app/db.py`、`ingestion.py`、`bm25.py`、`log.py`（B 类） | `datetime.now()` → `market_stamp()` |
| `docker/docker-compose.yml` | 显式 `TZ=Asia/Shanghai`（**仅作防御/日志可读**，代码已不依赖进程时区） |

## 3. 关键问题：**是否必须重跑 `backfill_publish_ts.py`？**

### 3.1 分析（结论：**很可能不需要**）

- 存量 `publish_ts` 由 `scripts/backfill_publish_ts.py` 在**宿主**写入（2026-09-10，282s，日志 `logs/backfill_ts.txt`）；
- 宿主时区 = **UTC+8**，且该脚本用的是"本地时间 → epoch"，即 **CST 时刻的 epoch**；
- 改为显式 CST 后，同一日期字符串产生的 epoch **完全相同**（例如 `2026-08-15` → `1786723200`，实测宿主当前值一致）。

→ **代码修正后，存量值不需要变**；真正的问题只是"其它时区的进程会算出不同边界"，属**代码缺陷**而非数据缺陷。

### 3.2 但必须先做一次前置扫描（防止例外）

```text
扫描 Qdrant 全部 109,554 点：比较 publish_ts 与 CST 解释下的期望 epoch
期望：0 处不一致
若 >0：说明有部分值是在 UTC 环境写入的 → 才需要重跑回填（282s）
```

⚠️ **该扫描依赖 Qdrant，而 Docker Desktop 当前已停止**（引擎不可达、0 进程）→
这是 Step 5 的**第一步前置检查**，需要你先启动 Docker Desktop（或改用本地模式副本，但副本早于回填，不含 `publish_ts`，无法替代）。

## 4. 测试计划（新增约 6 个）

1. `to_market_epoch("2026-08-15") == 1786723200`，且**与进程时区无关**（对照显式 UTC+8 构造）；
2. 边界回归：`date_from='2026-08-15'` 时，`publish_time='2026-08-15 00:30:00'` 的文档**必须被包含**
   （这是修复前在 UTC 容器下会被漏掉的那一类）；
3. `_cninfo_ts_to_date(ms)` 在任意进程时区下返回同一 CST 日期；
4. `market_today()` 在 UTC 16:00–24:00 区间与 UTC 日期不同（断言"按市场日历"的设计选择）；
5. 审计时间戳统一：`market_stamp()` 与 `created_at` 既有格式一致（`%Y-%m-%d %H:%M:%S`）；
6. 现有 183 个测试全绿（含评测相关，评测集不含 `days`，故评测数字不应变化）。

## 5. 风险与影响面

| 风险 | 说明 | 处置 |
| --- | --- | --- |
| **`days` 查询结果变化** | 边界日 00:00–08:00 的文档从"被排除"变为"被包含"（这正是修复目标）；UTC 16:00 后市场"今天"与 UTC"今天"差一天 | 在文档中显式声明；Docker 复测一次带 `days` 的检索 |
| B 类时间戳语义变化 | 若既有值按本地时间写入，本机同为 UTC+8 → **无变化**；容器内才体现差异 | 在文档中声明口径 |
| `publish_time` 是否需要重抓 | cninfo 日期转换此前在宿主（UTC+8）完成，结果与 CST 一致 → **无需重抓**；仅容器内运行时才会错 | 前置扫描同时校验日期集合是否自洽 |
| 未来海外市场 | 固定 +8 对海外数据是错的 | 记入技术债（需 per-market 时区字段），本期不做 |
| 评测可比性 | 评测集不含 `days`/日期过滤 → **评测数字不受影响** | 若受影响需重跑并留档 |
