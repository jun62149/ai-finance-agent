## A. Dense 与 BM25 的过滤语义是否等价？

### A0. 实际执行顺序（源码事实）

```text
query
 ├─ Dense 分支: app/rag/retrieval.py:97 → indexing.semantic_search → vector_store.search
 │    └─ Qdrant query_points(query_filter = Filter(must=[stock_code?, doc_type?, publish_ts Range?]))
 │       ★ 过滤在引擎内、与向量检索同时进行 → 候选空间 = 「过滤后的全部点」
 │    → 返回过滤集合内的 top-20（dense_top_k）
 │
 ├─ BM25 分支: app/rag/retrieval.py:107 → bm25.BM25Index.search
 │    ├─ retriever.retrieve(k=window)   window = max(top_k*10, 200)（有过滤时）
 │    │   ★ 先做全局词面检索，候选空间 = 「全库词面 top-200」
 │    └─ 再在 200 条里按 stock_code / doc_type / 日期 逐条 continue 过滤
 │        → 返回过滤后至多 top-20
 │
 └─ reciprocal_rank_fusion([dense_hits, lexical_hits], k=60)   （app/rag/hybrid.py:27-44）
      └─ 按 chunk_id 归并、等权累加 1/(k+rank)
 → reranker.rerank(query, fused, top_k)                      （app/rag/reranker.py）
```

**明确结论：两个分支的候选空间实际上不同。** Dense 是「先过滤再检索」（精确、覆盖全量），
BM25 是「先检索再过滤」（受 200 条窗口限制）。这不是文档措辞问题，而是**架构不对称**，并直接导致 C 项漏召回。

### A1. 空 `publish_time` 字段：两分支判定相反

| 字段 | 内容 |
| --- | --- |
| **1. 文件路径** | `app/rag/bm25.py:169-173`；`app/rag/vector_store.py`（`_build_filter` / `publish_ts_from`） |
| **2. 函数/类** | `BM25Index.search`；`ChunkVectorStore._build_filter` |
| **3. 当前实际实现** | BM25：`published = str(meta.get("publish_time") or "")[:10]`，随后 `if date_from and published and published < date_from: continue` —— **`published` 为空串时整个条件为假 → 不过滤、直接放行**。<br>Dense：日期条件编译为 `FieldCondition(key="publish_ts", range=Range(gte=..., lte=...))`；`publish_ts` 缺失/为 null 的点**不满足 range → 被排除**。 |
| **4. 为什么存在风险** | 同一查询下两条分支的候选集合语义不同：BM25 会返回"没有发布时间"的文档，Dense 不会。RRF 融合的是两个**定义不同的集合**，一旦语料中出现无时间文档，指标与线上行为都会出现只有 BM25 能召回的隐形偏差，且**无任何告警**。 |
| **5. 能否复现** | ✅ 可复现。`logs/audit_b1_filters.py`（构造 3 条：`publish_time=None` / `2026-08-15` / `2026-06-01`，同一 Qdrant + BM25 索引）：<br>`date_from='2026-08-01'` → `dense=['cB']`，`bm25=['cB','cA']`，差异 = 仅 BM25 返回 `cA`（`publish_time=None`） |
| **6. 严重程度** | **P3**（当前语料 963→12,366 篇文档中，`publish_time` 为空者 **0 条**，见 §F 数据核对；属未触发的正确性缺口） |
| **7. 推荐修法** | 二者择一并**在两分支同时实现**：(a) "无时间视为不满足日期过滤" → BM25 改成 `if date_from and (not published or published < date_from): continue`；(b) "无时间视为最早" → Dense 侧对 null 值做 `IsEmptyCondition` 的 OR 分支。推荐 (a)（更符合"最近 N 天"的直觉）。 |
| **8. 修复后影响** | 当前语料下评测/线上数字**不变**（无受影响文档）；需新增 1 个单测锁定语义；若未来接入无发布时间的数据源，行为由"隐形偏差"变为"明确排除"。 |

### A2. 候选空间不对称（设计取舍，非 bug，但需知情）

- Dense：过滤下沉到 Qdrant，候选 = 过滤后全量点；
- BM25：候选 = 全库词面 top-200，然后再过滤。

**风险**：`search_financial_knowledge(stock_code=..., doc_type=..., days=...)` 这类**多过滤组合**下，
BM25 的召回能力取决于"该文档是否在全局前 200 名词面命中里"，与过滤条件的选择性无关 —— 见 C 项。
**严重度 P2**（架构层面），**修法**见 C 项（推荐改用 Qdrant 稀疏向量，把过滤对称地沉到引擎）。

## B. `_date_to_epoch` 的时区是否存在 off-by-one 风险？

| 字段 | 内容 |
| --- | --- |
| **1. 文件路径** | `app/rag/vector_store.py`（`_date_to_epoch` / `publish_ts_from`）、`app/rag/retrieval.py:79-82`（`days` → `date_from`）、`scripts/backfill_publish_ts.py` |
| **2. 函数/类** | `_date_to_epoch(value, end_of_day=False)`；`hybrid_search` 的 `days` 分支 |
| **3. 当前实际实现** | `datetime.strptime(text, "%Y-%m-%d")` + `.timestamp()` → **按进程本地时区**转 epoch；`date_to` 用 `end_of_day=True` 补到 23:59:59。<br>`days` → `date_from = (date.today() - timedelta(days=days)).isoformat()`，随后同样进入上述转换。 |
| **4. 为什么存在风险** | 写入侧（`publish_ts` 回填、`upsert_chunks` 派生）与读取侧（过滤边界）**都依赖"当时进程的本地时区"**。宿主是 UTC+8，Docker 容器是 UTC（实测容器 `time.timezone=0`）→ 同一个日期字符串在两侧相差 28800 秒。 |
| **5. 能否复现** | ✅ 数值可复现，无需构造数据：<br>宿主：`_date_to_epoch('2026-08-15')` = **1786723200**（= 2026-08-15 00:00 +08）<br>容器：`docker exec ai-finance-api python -c "int(datetime.strptime('2026-08-15','%Y-%m-%d').timestamp())"` = **1786752000**（= 2026-08-15 00:00 UTC）<br>差值 = 28800s。存储值由宿主写入（如 `000725` 的 `2026-08-31` 文档 → `1788105600`），容器内 `date_from='2026-08-31'` 的边界比它大 8 小时 → **该文档被排除**。 |
| **6. 严重程度** | **P2**（仅影响 Docker 部署；表现为"最近 N 天"的窗口边界整体偏移 8 小时：`date_from` 侧少含边界日 00:00–08:00 的文档，`date_to` 侧多含 8 小时） |
| **7. 推荐修法** | ① 让所有 epoch 转换显式 UTC（`datetime.strptime(...).replace(tzinfo=timezone.utc).timestamp()`）；② **同一次提交内重跑一次 `scripts/backfill_publish_ts.py`**（否则只是把偏差从一侧搬到另一侧）；③ 或在容器内固定 `TZ=Asia/Shanghai` 作为过渡方案（治标，且依赖部署环境）。推荐 ①+②。 |
| **8. 修复后影响** | `publish_ts` 全量重写（109,554 点，上次耗时 282s）；日期相关单测需补 UTC 断言；评测若使用 `days` 需重跑（当前评测集不含 `days`，故评测数字不变）。 |

**回答评审的具体问题**：> "如果用户要求'最近 7 天'，Dense 和 BM25 是否一定使用完全相同的时间边界？"

**不是。** 两者用的是**同一个 `date_from` 字符串**（`retrieval.hybrid_search` 计算一次后同时下发），
但**转化成边界的机制完全不同**：Dense 把字符串转成 epoch 后交给 Qdrant 做数值比较（受时区影响、且对缺失字段严格排除），
BM25 直接做**字符串前 10 位比较**（不受时区影响、且对空值放行）。
因此"同一时间边界"只在**同一时区 + 时间字段齐全**的前提下成立。

## C. BM25 后置过滤是否可能因 candidate window 太小而漏召回？

| 字段 | 内容 |
| --- | --- |
| **1. 文件路径** | `app/rag/bm25.py:153-155`（窗口）与 `:157-177`（后置过滤） |
| **2. 函数/类** | `BM25Index.search` |
| **3. 当前实际实现** | `filtered = bool(stock_code or doc_type or date_from or date_to)`<br>`window = min(len(self.chunk_ids), max(top_k * 10, 200) if filtered else top_k)`<br>`results, scores = self.retriever.retrieve([tokens], k=window, sorted=True)` → 之后逐条 `continue` 过滤。<br>**即：任何过滤条件存在时，最多只扫描全局词面前 200 条。** |
| **4. 为什么存在风险** | 过滤条件越窄（如"某一只股票 + 公告 + 时间窗"），目标文档越不可能出现在全局前 200 名里 → **直接 0 命中**。调用方（Agent / RAG Tool）无法区分"库里没有"与"窗口太小没扫到"，**无异常、无日志**。 |
| **5. 能否复现** | ✅ 可复现，且不是构造出来的极端案例。`logs/audit_b1_window.py`（真实 109,554 语料，对比"窗口版 = 实际代码"与"全量扫描后过滤 = 理论无损失"）：<br>`query='公告' stock=000333 doc_type=announcement` → **窗口版 2 命中 vs 全量版 356**<br>`'公告'/000725` → 20 vs 673；`'公告'/600519` → 10 vs 234；`'公告'/002594` → 14 vs 337<br>`'回购'/600519` → 20 vs 157；`'回购'/000725` → 20 vs 531<br>**4 个查询 × 4 只股票 = 16/16 组合全部出现召回损失。** |
| **6. 严重程度** | **P1**（过滤场景正是 Agent 的主用法：`stock_code` 21/36 题、`doc_type` 35/36 题的评测集也证明这一点；且失败是静默的） |
| **7. 推荐修法** | 短期（缓解）：过滤存在时把窗口放大到与过滤选择性相称（如 5,000，代价是 bm25s 排序开销，实测 109k 全量扫描约数百 ms）；<br>中期（推荐）：**改用 Qdrant 稀疏向量（BM25 权重）+ 与 dense 相同的 payload 过滤**，让过滤下沉到引擎，两分支候选空间对称；<br>长期：保留 bm25s 但按过滤维度预建子索引（按 stock_code 分组）。 |
| **8. 修复后影响** | BM25 与 Hybrid 的评测数字都会变化（预计上升，尤其带过滤的题）；需要重跑四组对照并更新 README 表格；`search_hybrid.py --mode bm25` 的延迟会上升；需补"窗口 vs 全量"回归测试。 |

## D. RRF 归因（源码分析 与 实验数据 分开报告）

### D-1 源码分析（不含测量）

| 字段 | 内容 |
| --- | --- |
| **1. 文件路径** | `app/rag/hybrid.py:27-44`；调用点 `app/rag/retrieval.py:114-116` |
| **2. 函数/类** | `reciprocal_rank_fusion(result_lists, k=60, top_k=None, score_keys=("dense_score","bm25_score"))` |
| **3. 当前实际实现** | `entry["rrf_score"] += 1.0/(k + rank)`，两路**等权**；按 `chunk_id` 归并；无权重参数、无 doc 级去重（文档去重发生在评测口径 `eval_metrics.score_run`，不在融合层）。`k` 由 `Config.RRF_K=60` 提供。 |
| **4. 为什么存在风险** | 等权融合对"两路质量差异大"的场景不友好；且**文档级去重发生在融合之后**，融合本身对"同一文档的多 chunk"没有降权，可能让单文档多 chunk 挤占融合前列（与 C/B 的候选空间差异叠加）。 |
| **6. 严重程度** | **P1**（影响对外评测结论的可信度，见 D-2） |

### D-2 实验数据（与上面的源码分析分开）

**实验 1：两路候选重合率**（`logs/audit_b1_overlap.py`，36 题，带过滤设定，各取 20）

```text
chunk 级 Jaccard 均值 = 0.2091
document 级 Jaccard 均值 = 0.2945
平均：dense 唯一文档 14.4 | bm25 唯一文档 14.7 | 共同文档 6.1
```

→ **两路确实互补**（约各有一半文档是对方没有的），融合在理论上有价值。

**实验 2：发现评测口径缺陷（chunk 预算不等）** ⚠️

官方脚本 `scripts/evaluate_retrieval.py` 中，四配置的**取回预算并不相同**：

```text
BM25-only : index.search(top_k=10)                      → 10 个 chunk
Dense-only: semantic_search(top_k=10)                   → 10 个 chunk
Hybrid    : semantic_search(top_k=20) + bm25(top_k=20)  → RRF → 15 个 chunk → 截到 10
```

由于**同一文档会被切成多个 chunk**，10 个 chunk 常常只覆盖 3~8 篇文档；`score_run` 按 document 去重后再算
Recall@K，因此**列表长度（=不同文档数）直接决定 recall**。逐题复现（`logs/audit_b1_recon.py`）：
某题 `top_k=10` 返回 10 个 chunk 但只有 **3 篇不同文档**，`top_k=20` 则有 **8 篇**。
→ 说明"BM25/Dense 的 10-chunk 预算"被系统性低估，而 Hybrid 拿了 15。

**实验 3：等预算（20 chunk）复测**（`logs/audit_b1_fair.py`）

| 配置 | 等预算 R@5 | 等预算 R@10 | 等预算 MRR | 官方（不等预算）R@5 |
| --- | --- | --- | --- | --- |
| BM25-only | **0.4351** | 0.5332 | 0.6672 | 0.4240 |
| Dense-only | 0.3922 | 0.4766 | 0.5752 | 0.3784 |
| RRF k=60 等权 | 0.4248 | 0.5484 | 0.6862 | 0.4109 |
| RRF k=10 等权 | **0.4387** | 0.5471 | 0.6871 | — |
| RRF 加权 w_dense=1, w_bm25=3 | **0.4427** | **0.5549** | **0.7068** | — |

**实验 4：RRF@5 相对 BM25@5 的得失**（k=60）

```text
有新增相关文档的题数 = 11   ｜   丢失相关文档的题数 = 14   （共 36 题）
```

### D-3 回答："为什么 metadata filter 场景下 Hybrid(RRF) R@5 = 0.4109 反而低于 BM25-only 0.4240？"

**逐条回应评审列出的 5 个候选原因：**

1. **两路候选重合率**：chunk 级 Jaccard 仅 0.209、document 级 0.295 → **两路互补，不是"高度重合导致融合无意义"**。评审的怀疑不成立。
2. **RRF 前后排名变化**：11 题获益 / 14 题受损 → 净负，**与观察到的 R@5 下降方向一致**，是直接原因。
3. **是否因为 document 去重**：去重不改变"等预算对比"的结论；但它**放大了 chunk 预算不等的影响**（实验 2），这是官方数字失真的放大器。
4. **是否因为 top-k**：**是重要因素**。等预算下 k=60 仍低于 BM25（0.4248 vs 0.4351），但 **k=10（0.4387）与 bm25 加权 w=3（0.4427）都反超 BM25** → 结论对 `RRF_K` 与权重**高度敏感**。
5. **是否因为标签天然偏向 BM25**：无法在 Batch 1 内定量剔除（需按题重标注或分层），**当前判断：部分成立**（标签由标题关键词生成），但**不足以解释全部差距**——因为 remedy 只需调 k/权重即可反超，说明差距主要是融合参数问题。
6. **其他实现因素**：**发现一个实现层面的因素**——`reciprocal_rank_fusion` 对"同一文档的多个 chunk"不做文档级降权，而评测在 document 级计算，二者口径错位；此外 BM25 分支的 200 窗口（C 项）在这个评测里也会**同时**压制 BM25 自身的召回，使"BM25 vs Hybrid"的比较建立在两个都被扭曲的分支上。

**对评审"不要直接接受等权稀释强信号"的回应**：接受批评 —— 我原先的解释**方向对但不完整**：
真正可复现的机制是「**k 值/权重敏感** + **评测 chunk 预算不等**」，而不是"过滤导致候选变小所以稀释"（后者无法解释等预算下 k=10 就能反超）。

| 字段 | 内容 |
| --- | --- |
| **6. 严重程度** | **P1**（对外公布的对照表口径不一致；结论"Hybrid+Rerank 最优"仍成立，但"BM25 vs Dense vs Hybrid"三者的排序在**修正口径后会变化**：等预算下 BM25-only(0.4351) > RRF k=60(0.4248)） |
| **7. 推荐修法** | ① 评测脚本统一 chunk 预算（并在报告中标注预算）；② 结论表用**同一预算**重算；③ 把 `RRF_K` 与权重纳入评测扫描，给出选定依据；④ 融合层增加可选的**文档级去重/降权**，与评测口径对齐。 |
| **8. 修复后影响** | README 的对照表数字需整体更新（四组都变），结论表述需改为"等预算 R@5 下 …"；`evaluate_retrieval.py` 的 `--top-k` 语义需明确为"chunk 预算"还是"最终返回条数"；不影响线上检索逻辑（仅评测口径）。 |

| **3. 当前实际实现** | BM25 持久化内容 = bm25s 稀疏索引 + `chunk_ids` + `metadatas`（`chunks_meta.pkl`）。**没有** `embedding_version`、**没有**语料指纹、**没有**构建时间、**没有** collection 名、**没有**点数校验。<br>`build_bm25.py` 按 `embedding_version == 当前版本` 取 chunks 建索引 —— 但**没有任何机制保证版本变更后必须重建**：`retrieval.get_components()` 只是 `BM25Index.load()`，不比对 SQLite/Qdrant。 |
| **4. 为什么存在风险** | 两种**静默**失败路径：<br>(i) **新入库 + 已嵌入，但未重建 BM25** → 词面分支永久看不到新 chunk（漏召回，无报错）；<br>(ii) **chunks 被重灌（AUTOINCREMENT id 变化）** → BM25 元数据里的 `point_id` 可能指向**另一条 chunk**，`hybrid_search` 回表补正文会取到**张冠李戴的正文**；而 `rag_tools._to_evidence` 的必填字段校验（`chunk_id/document_id/stock_code/doc_type/title/source/publish_time/url`）**不含 `content`**，仍会通过校验并把错误正文交给 LLM。<br>此外 `EMBEDDING_VERSION` 变更本身**不会**使 BM25 失效（chunk id 与正文不变），真正危险的是 **chunk 集合变化**——这一点在代码里没有任何区分与提示。 |
| **5. 能否复现** | （a）当前状态检查 **PASS**：`BM25 chunk_id 集合 == Qdrant payload chunk_id 集合 == SQLite chunks 行数 == 109,554`，双向差集均为 0；抽样 5,000 个 `point_id` 在 `chunks` 表全部命中（`logs/audit_b1_window.py`）。<br>（b）"忘记重建"的失败**未构造实际漂移**（那会污染生产数据，且评审要求不改数据）；已通过代码路径分析给出结论 —— 因此这一条对"行为"是 **UNVERIFIED**，对"缺少防护机制"是 **CONFIRMED**。 |
| **6. 严重程度** | **当前 P2**（一致但无保障）；一旦漂移 → **P1**（静默错误正文进入 LLM 报告） |
| **7. 推荐修法** | ① BM25 索引旁写 `manifest.json`：`{embedding_version, chunk_count, chunk_id_fingerprint(sha256 of sorted ids), built_at, collection}`；<br>② `BM25Index.load()` 或 `get_components()` 做**轻量校验**（数量 + 指纹），不一致直接抛结构化错误（如 `IndexOutOfSync`），**不静默降级**；<br>③ `hybrid_search` 对"BM25 命中但回表无正文"显式丢弃并计数（当前是静默空正文）；<br>④ `_to_evidence` 的必填字段补 `content`（非空）或明确允许空并在证据上标注。 |
| **8. 修复后影响** | 新增错误码会影响 `search_financial_knowledge` 的失败语义与工具测试；启动校验会带来一次全量 chunk_id 读取（109k 行，约几百 ms）；需重跑一次 `build_bm25.py` 生成 manifest。 |
