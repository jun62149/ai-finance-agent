## 3. 隔离 BM25 窗口的效果（同协议 A/B）

为了把"窗口修复"与"评测协议变更"分开，以下两次运行**协议完全相同**（candidate/fusion/final=20），
仅 `BM25_WINDOW` 不同：`200` 复现修复前的截断行为，`0` 为修复后。

| config | R@5 (window=200) | R@5 (全库) | MRR (200 → ALL) | 逐题有差异的题数 | 其中"窗口版返回更少"的题数 |
| --- | --- | --- | --- | --- | --- |
| bm25 | 0.4351 | **0.4351** | 0.6672 → 0.6672 | **6 / 36** | **6** |
| dense | 0.3922 | 0.3922 | 0.5752 → 0.5752 | 0 / 36 | 0 |
| hybrid | 0.4248 | 0.4248 | 0.6862 → 0.6847 | 3 / 36 | 0 |
| hybrid+rerank | 0.4841 | 0.4563 | 0.7271 → 0.7119 | 4 / 36 | 0 |

**结果解读（如实记录，不美化）**：

1. **修复对 headline 指标没有提升**：BM25-only 的 R@5/R@10 在两种窗口下完全相同；
2. 但**逐题层面确实存在截断伤害**：`bm25` 有 **6/36 题**在窗口模式下返回的 chunk 更少
   （A01、A03、C01、C05 等，均带 stock/doc_type/date 过滤），只是这些题的相关文档排名靠前，
   没有影响聚合指标 —— 即**修复恢复的是"召回完整性"，不是分数**；
3. `hybrid+rerank` 的 0.4841 → 0.4563 差异 = **0.0278 = 恰好 1/36**，属**单题翻转（噪声）**，
   不应解读为"修复使 rerank 变差"；同理 hybrid 的 MRR 波动（0.6862 → 0.6847）也在噪声范围内；
4. `dense` 不受影响（0/36 差异）✓ —— 符合预期，它不走 BM25 分支。

## 4. 回归护栏（评审要求）

**不带过滤**的两次运行（window=200 vs 全库）在**四个配置上逐题完全一致（0/36 差异，四位小数相同）**。

这正是预期的：无过滤时旧代码的窗口就等于 `top_k`，全库后前 20 名不变。
该结果证明本次改动是**外科手术式**的，没有触碰过滤之外的行为。

## 5. 一个重要发现：当前评测集**没有覆盖**这个失效模式

- 触发漏召回的真实案例是「**泛化词 + 窄过滤**」：`query='公告'` + `stock_code=000333` + `doc_type=announcement`
  → 修复前 **2 命中**、修复后可达 **356 条**（见 `docs/bm25_latency_comparison.md`）；
- 但 36 题评测集**没有这种题**（评测 query 都是具体问题，不是泛化词），因此：
  - 聚合指标看不出修复收益（第 3 节），
  - **回归保护只能依靠单元测试**：`tests/unit/test_bm25_window.py::test_window_mode_misses_the_target_full_mode_finds_it`
    （构造 240 条高分文档 + 10 条目标文档，目标排名在窗口之外 → 窗口模式 0 命中、全库模式全部召回）；
- **建议（未执行，待评审决定）**：评测集后续可增加 1~3 条「泛化词 + 窄过滤」样本，
  让这类失效在指标层面也可观测。改评测集需谨慎（会改变可比性），故此处只提出建议。
